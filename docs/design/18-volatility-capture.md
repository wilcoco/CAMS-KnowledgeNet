# 18 — 휘발성 포획: 사례를 우리 기능으로 (기획 라운드테이블 + 총괄 결정)

> 입력 사례: [`../refs/llm-volatility-external-layer.md`](../refs/llm-volatility-external-layer.md)
> ("Claude Code 사용량" 질문 — 표준답 `claude-monitor`(가짜 천장) → 검증 실패 →
> 원인(로컬 로그 역산) → 교정(공식 `rate_limits` statusline)). 그 교정이 모델
> 안에선 휘발 → **외부 지식/평가 층(=우리)이 포획**해야 다음 사람 ①에 주입된다.
>
> 이 노트는 *"이 사례가 우리 서비스에서 실제로 작동하려면 무엇을 고쳐야 하나"*를
> 경력 다른 기획자 5명에게 묻고, 엔트로픽 기획 총괄이 결정한 결과다.

---

## 0. 사례가 우리에게 요구하는 것 (한 줄씩)

1. 다음 사람이 같은 질문을 하면 **교정답(④)이 표준답(①) 위에 먼저** 떠야 한다.
2. 교정답에는 **적용 조건**이 붙어야 한다("statusline은 Pro/Max 한정").
3. 교정답은 **썩는다** — 공식 API가 나오면 비공식 경로는 deprecated. 신선도 신호 필요.
4. 위 셋이 동작하려면 *무엇이 좋은 교정인가*를 **평가·랭킹**해야 한다(= 우리 권위/안목).

4번(심장)은 이미 hub-authority(노트 13)로 구현됨. 라운드테이블의 쟁점은 **1·2·3**.

---

## 1. 라운드테이블 — 5인의 의견 (각자 다른 직업적 편향)

### P1. 검색·랭킹 출신 (전 IR/랭킹 엔지니어)
> "이 사례의 전부는 **'교정답이 검색에서 먼저 뜨는가'** 한 문장이다. 나머지는 장식이다.
> 우리는 `ask`가 채택본을 `stage:"existing"`으로 먼저 보여준다 — 좋다. 그런데 그
> 채택본이 **'최초 표준답'인가 '권위 1등 교정답'인가?** 코드상 동일 슬러그의 *채택된*
> 노드를 집어오는데, 표준답이 먼저 채택돼 스테이크가 쌓여 있으면 교정(fork)이 더
> 높은 권위여도 옛 답을 돌려줄 위험이 있다. **`existing` 경로를 슬러그 군집 내 권위
> 최댓값으로 못박아라.** 그리고 신선도는 *배지가 아니라 랭킹 피처*여야 한다 — 오래된
> 답은 점수에서 깎여야 검색 상단에서 자연히 내려간다."

### P2. 개발자도구 PM (전 Stack Overflow/DevTools)
> "사례의 진짜 가치는 ④ 교정답이 아니라 **③ 원인 규명**('로컬 로그 역산 → 가짜
> 천장')이다. 교정답만 저장하면 다음 사람은 '왜 monitor를 쓰면 안 되는지' 모른 채
> 'statusline 써라'만 받는다 — 그러면 monitor가 다시 표준답으로 부활할 때 방어가 안
> 된다. **반례(왜 표준답이 틀렸나)가 교정 노드에 묶여야** 한다. 우리 `대립`
> 릴레이션이 바로 이거다 — fork가 원답을 `대립`으로 가리키게 하고, 그 본문에 *반증
> 근거*를 담게 하라. 검증이 **싸야** 한다는 것도 핵심: 발자국 한 번이 곧 검증이다.
> 발자국에 '확인함/반증함' 같은 미세 의미를 얹을지는 신중히 — 노동화 금지선(노트 17)."

### P3. 위키·커뮤니티 운영자 (전 Wikipedia/포럼 운영)
> "내 관심은 **3번, 부패**다. 위키가 죽는 이유는 틀려서가 아니라 **낡아서**다. 우리는
> `answered_at`이 이미 있으니 토대는 있다. 필요한 건 ① 신선도 배지(🟢/🟡/🔴),
> ② **재검 넛지** — 오래된 채택답을 시스템이 '아직 유효한가?' 물어 사람이 갱신/환수
> 하게. 단 *자동 폐기는 절대 금지* — 사람이 판정한다(우리 제1원리). LLM Wiki의 Lint를
> 우리식으로: **AI는 후보(낡음 의심)만 제시, 갱신은 사람.** 그리고 정정-환수(노트 13)가
> 거버넌스 레버다 — 낡은 답을 교정하면 스테이크가 교정자에게 흐른다."

### P4. 온톨로지·지식그래프 설계자
> "**2번, 맥락 조건화**가 빠지면 이 사례는 오히려 *오염*이다. 'statusline이 낫다'를
> 무조건 띄우면 웹만 쓰는 사람에겐 **틀린 답**이다. 같은 질문에 답이 둘인데 둘 다 맞고
> *조건이 다를 뿐*인 경우를 우리는 fork(대립)로만 다룬다 — 그건 '둘 중 하나가 틀림'을
> 함의해서 부적절하다. 필요한 건 **조건 패싯**(레이어/버전/환경): '이 답은 {Pro/Max}
> 에서'. 우리 `전제(prerequisite)` 릴레이션이 8할 근접하나, 전제는 *다른 노드*를
> 가리키는 관계지 *이 노드에 붙는 라벨*이 아니다. 가벼운 **조건 태그**를 노드/교정에."

### P5. 그로스·행동경제 (전 성장팀, 회의론자)
> "다 좋은데 — **사람이 안 채운다.** 조건 태그, 신선도 입력, 반증 근거… 전부 *추가
> 노동*이고 우리는 '귀찮음이 적이다'(노트 13)·'노동화 금지'(노트 17)를 이미 정했다.
> 필드를 늘리면 빈 필드만 는다. 원칙: **사람에게 새 입력을 강요하지 마라.** 조건·신선도는
> *AI가 제안 → 사람이 한 번 탭으로 확인*(노트 16 시멘틱 릴레이션과 똑같은 패턴)이어야
> 한다. 신선도 배지는 사람 입력 0(시계가 계산). 조건 태그도 AI가 본문에서 뽑아 칩으로
> 제시, 사람은 틀린 것만 떼면 된다. **새 폼을 만들지 말고, 이미 있는 제스처에 얹어라."

## 2. 쟁점 충돌 지도

| 쟁점 | 누가 밀어 | 누가 견제 | 핵심 긴장 |
|---|---|---|---|
| 교정답 검색 상단 보장 | P1 | (합의) | `existing` 경로가 권위 최댓값을 못박는가 |
| 반증 근거(③) 포획 | P2 | P5(노동화) | 별도 필드 vs `대립` 본문에 흡수 |
| 신선도 배지·재검 | P3 | P5(입력 강요?) | 자동 계산이면 P5도 동의 |
| 조건 패싯 | P4 | P5(빈 필드) | 강제 폼 vs AI제안+탭확인 |
| 자동 폐기 | — | P3(절대 반대) | 판정은 언제나 사람 |

## 3. 엔트로픽 기획 총괄 — 결정

> 원칙 재확인: **(a)** 사례의 90%는 "교정답이 먼저 뜨는가"다 — 거기에 자원을 몰아라.
> **(b)** 사람에게 새 폼을 강요하지 않는다 — 모든 신규 신호는 *시계 자동* 또는
> *AI제안→탭확인*. **(c)** 판정·갱신·폐기는 언제나 사람(제1원리).

우선순위와 결정:

### P0 — 교정답 우선 노출 보장 (이게 안 되면 나머지 무의미) ✅ 즉시
- **`ask`의 `existing` 경로를 '동일 슬러그 군집의 권위 최댓값 노드'로 못박는다.**
  현재 채택본(스테이크>0)을 집어오되, **fork/교정을 포함한 군집 전체에서 `authority_in`
  최댓값**을 고른다. → 표준답이 먼저 채택돼 있어도, 더 높은 권위의 교정이 있으면 그게
  먼저 뜬다. (P1 채택)
- **`/api/synthesize`는 교정·신선·고권위 답을 근거 상단에** 둔다(이미 권위정렬 — 신선도
  가중만 추가).

### P1 — 신선도(부패) 신호: 시계 자동, 입력 0 ✅ 즉시 (P3+P5 합의)
- **신선도 배지**: `answered_at`/`updated_at` 기준 경과로 🟢신선(≤90d)·🟡(≤365d)·
  🔴오래됨(>365d). 사람 입력 0. `_node_view`에 `freshness` 추가.
- **랭킹 약가중**(P1): 권위에 곱하는 *완만한* 신선도 계수(오래됨일수록 소폭 감액) —
  교정/갱신 시 시계 리셋. 단 권위를 압도하지 않게(부패는 tie-breaker급).
- **재검 넛지**: 🔴 + 채택본이면 "아직 유효한가요?" 한 줄 — 누르면 *갱신(시계 리셋)*
  또는 *정정(fork)* 으로 보낸다. **자동 폐기 없음**(P3). = LLM Wiki Lint의 우리식
  (AI는 후보만, 사람이 판정).

### P2 — 맥락 조건화: AI제안 + 탭확인 (새 폼 금지) ✅ 다음
- **조건 패싯**을 노드에 `conditions: list[str]`로(예: `["Claude Code Pro/Max"]`).
  입력 경로는 **AI가 본문에서 추출 → 칩으로 제시 → 사람이 틀린 것만 제거**
  (노트 16 릴레이션 확인과 동형 — 새 폼 안 만든다). (P4 실현 + P5 제약 충족)
- 조건이 다른 동급 답은 fork(대립) 대신 **같은 슬러그에 공존**시키고 조건 칩으로 구분.
- `/api/synthesize`·검색은 조건 칩을 *필터/주석*으로 노출("이 답은 Pro/Max 한정").

### P3 — 반증 근거(③ 원인) 포획: 별도 필드 X, `대립` 본문으로 ✅ 다음
- fork(정정)가 원답을 **`대립` 릴레이션**으로 가리키게 하고(이미 가능), 그 fork 본문에
  *왜 표준답이 틀렸나*(반례·실측)를 담게 **플레이스홀더로 유도**. 새 스키마 없음. (P2
  실현, P5 노동 최소화)

### 보류·기각
- ❌ 발자국에 '확인/반증' 미세 의미 얹기 — 노동화·금지선(노트 17). 발자국은 단일 제스처 유지.
- ❌ 강제 조건/신선도 입력 폼 — P5. 전부 자동 또는 탭확인.
- ⏸ 조건 패싯의 *검색 필터화* — 데이터 쌓인 뒤(콜드스타트엔 과함).

## 4. 구현 계획 (파일별, 그라운디드)

| 단계 | 파일 | 변경 |
|---|---|---|
| P0 | `unified.py` `ask()` | `existing` 선택을 동일 슬러그 군집 `authority_in` 최댓값으로(채택본 우선이 아니라 *권위 우선*). force 동선 유지 |
| P0 | `unified.py` `synthesize()` | 근거 정렬에 신선도 약가중 추가 |
| P1 | `tree.py` | `freshness_of(node_id)`(경과→🟢/🟡/🔴 + 계수) 헬퍼; `authority_in`에 신선도 계수 곱(완만) |
| P1 | `unified.py` `_node_view` | `freshness` 필드; 🔴+채택본에 `recheck:true` 플래그 |
| P1 | `app.html` | 신선도 배지, "아직 유효한가요?" 넛지 → 갱신/정정 분기 |
| P2 | `tree.py` Node | `conditions: list[str]` 필드 + 직렬화(pgstore 마이그레이션 컬럼) |
| P2 | `unified.py` | 조건 추출 제안 엔드포인트(AI) + 확인/제거 API(릴레이션 패턴 재사용) |
| P2 | `app.html` | 조건 칩(제거 가능), synthesize/검색에 조건 주석 |
| P3 | `app.html` | fork 본문 플레이스홀더("왜 표준답이 틀렸나: 반례/실측") + `대립` 자동 제안 |

**테스트:** P0은 "교정이 표준답보다 권위 높으면 `ask`가 교정을 반환"하는 회귀 테스트가
정본(사례의 심장). P1은 시계 모킹으로 배지 경계. 두루·권위 기존 156 테스트 불변.

## 5. 한 줄 결론

이 사례를 우리 것으로 만드는 핵심은 **"교정답이 먼저 뜬다(P0)"** 하나이며, 조건(P2)·
신선도(P1)·반증(P3)은 *그 교정답을 오염·부패로부터 지키는 보조 신호*다. 셋 다
**사람에게 새 노동을 지우지 않는 방식**(시계 자동 / AI제안+탭확인)으로만 들인다 —
그래야 제1원리(사람이 판정, AI는 횃불)와 충돌하지 않는다.
