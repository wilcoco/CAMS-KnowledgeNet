# 통합 재귀 노드 모델 — 설계 정리 (2차)

**작성일:** 2026-06-01
**문서 성격:** 2차 설계 논의 정리본. [`01-design-notes.md`](01-design-notes.md)(정본)를
이어, 두 프로토타입(`mvp` 위키 + `service` 온톨로지)을 **하나의 재귀 노드 모델**로
수렴시킨 기획을 못박는다.

> 정본이 *무엇을 평가하고 왜 보상하는가*를 정했다면, 이 문서는 *그것을 담는 자료
> 구조를 어디까지 일반화할 수 있는가*를 정한다.

---

## 0. 한 줄 요약

> **한 노드 = 채워야 할 슬롯 하나.** 그 위에 "질문 → 답 → 보강·후속·정정·포크"라는
> **같은 모듈**이 **재귀적으로** 적용된다 (답 자체가 또 하나의 슬롯이므로). 위키 페이지,
> 열린 질문, 링크 스텁, AI 초안, 스레드 위의 모든 기여 — 전부 *같은 종류의 노드*다.

---

## 1. 출발점 — 발견된 직관

처음 짚은 직관은 이것이다:

> *"질문→답에 붙는 보강·후속·정정·다른답 모듈이, **다른 채워야 할 항목**을 채울 때도
> 있어야 한다."*

`service` 프로토타입은 **질문↔답** 쌍에만 이 모듈을 달았고, `mvp` 위키는 **페이지
본문**을 별도 개념으로 다뤘다. 두 프로토타입은 *같은 모듈을 서로 다른 슬롯에 따로
구현*하고 있었다. 일반화하면:

- "페이지를 채운다"도 슬롯 채우기다.
- "답을 단다"도 슬롯 채우기다.
- "답에 대한 보강을 단다"도 슬롯 채우기다 (답이 곧 새 슬롯).

→ **슬롯과 모듈을 분리하지 말고, 한 노드 종류와 한 모듈로 합치고 재귀시킨다.**

---

## 2. 모델 — 모든 것이 하나의 `Node`

```
Node = 채워야 할 슬롯
 └─ 같은 모듈: ask → answer → (augment | follow-up | correct | fork)
      └─ answer 도 Node → 그 위에 같은 모듈 (재귀)
```

| 기존 두 개념 | 통합 후 |
|--------------|---------|
| 위키 페이지 (mvp) | `Node` (질문=제목, 답=본문) |
| 질문/답 쌍 (service) | `Node` (같은 것) |
| 링크 스텁 `[[제목]]` | 아직 안 채워진 `Node` (DORMANT) |
| AI 초안 | `is_answer=True` 인 `Node` |
| 보강·후속·정정 | 답 노드를 부모로 하는 자식 `Node` |

핵심 불변식은 정본에서 그대로 계승한다 — **기여 노드는 부모 내용을 복사·상속하지
않고 참조만** 한다 (`f106c76`). 슬롯을 합쳐도 가치 귀속(누가 무엇을 채웠는가)은
흐려지지 않아야 하기 때문이다.

## 5. 코드 지도 (정본 프로토타입 지도에 추가)

```
src/nightwish/
├── tree.py            재귀 노드 모델 (정본 §4 + 슬롯 일반화)
├── wiki_economy.py    민팅·인도스·배당 (node id 키)
├── unified.py         통합 앱 — 한 그래프 / 한 HTTP 표면        [기본 진입점]
└── static/app.html    단일 페이지 UI ("업무 지식 정리")
```

> 정본의 한 줄 요약 — *"구조 자체가 다음 질문의 답이 된다"* — 은 그대로다. 이 문서가
> 더한 것은: **그 구조를 이루는 노드가 단 한 종류이고, 그것을 키우는 모듈도 단
> 하나이며, 답이 또 슬롯이 되어 끝없이 재귀한다**는 점뿐이다.
