## 2026-06 세션 — 통합 앱 안정화 + 평가=저작

### 결정

1. **통합 재귀 노드 모델 채택.** 위키 페이지·질문/답·기여를 한 종류 노드로 합치고,
   "질문→답→보강/후속/정정/포크" 모듈을 모든 슬롯에 재귀 적용. 두 프로토타입
   (`mvp`/`service`)은 **보존**(삭제 안 함). → `02-unified-recursion.md`
2. **앱 제목** = "업무 지식 정리".
3. **평가 = 저작** (사용자 요청). 인도스(평가)가 ① 평가자의 안목(hub) 적립,
   ② 공동저작 표기, ③ 평가가 곧 채택(검색 우선 노출)을 일으킨다. → §2.5
4. **"AI에게 묻기"는 항상 AI에게 묻는다.** 검색 결과가 밑에 떠도 묻기 버튼은 늘 새
   답을 생성. 기존 관련 답은 `related`로 함께 반환해 참고용으로만 노출. (이전의
   "검색-우선 재사용"은 새 질문에 옛 답을 돌려주는 문제가 있어 제거.)
5. **영속성은 Postgres 우선.** 임시 디스크 유실을 막기 위해 통합 앱도 `DATABASE_URL`
   있으면 Postgres에 저장(레거시 `mvp`와 동일). → `../operations.md`
6. **보상 위계 — 사람의 실질 기여 > 평가/투자 > AI 초안** (사용자 요청, 원칙 확정·구현 예정).
   AI로 뼈대를 빨리 만드는 건 *재료*(쉽고 쌈)이고, 희소한 가치는 *사람이 자기 지식·
   의견을 더하는 것*이다. 따라서 배당은:
   - **사람의 실질 기여**(보강·정정·자기 의견, `value_add`) → ★ 가장 큰 몫
   - **평가/투자(스테이크)** → 안목 보상은 하되 작게 (earliness×hub)
   - **AI 초안**(frozen, 프롬프트로 뽑은 것) → 거의 0 (재료; 띄운 사람에겐 소액 안목만)
   인코딩: 기존 부가가치 게이트(`value_add`)에 **기여 종류별 가중치** 추가 — AI-frozen은
   배당 계수 낮게, 사람 실질 기여는 높게. "AI에게 묻기만 한 사람"이 author로 큰 배당
   받는 것 방지. **평가=저작은 유지하되 분배는 콘텐츠 창작자 우선**(평가는 *신호*,
   보상의 큰 몫은 창작자). 위험: "실질 기여" 측정(길이≠질, 게이밍) → 신호는 "사람이
   직접 쓴 value_add + 높은 안목 평가자의 평가". (구현 시 `wiki_economy.endorse`
   분배식·`value_add` 계수 조정.)

### 미해결 / 다음 후보

- **[상용 LLM 비용·데이터 정책]** *(나중에 해결)* — 무료 LLM API로 상용 서비스가
  가능한가? 결론: 데모/MVP는 가능, 본격 상용은 무리. 벽 4가지 — ① rate limit
  ② SLA 없음 ③ **무료 tier는 보낸 데이터를 학습에 쓸 수 있음(기밀 업무지식 유출
  위험, 치명적)** ④ ToS 상업 제한. 상용 전환 시: no-training 보장되는 **유료
  종량제** 또는 **자체 호스팅 오픈모델**로. 구조는 `set_ai(fn)`로 LLM-무관이라
  무료로 시작→나중에 교체해도 코드 거의 안 바뀜. (실채택 전 각 서비스의
  "data used for training?" + 상업 허용 조항 직접 확인.)
- **검색/목록 읽기 점-조회화** — 현재 `/api/state`·`get_node`만 점-조회. `search`·
  `scores`·`list_nodes`는 아직 전체 로딩(검색·랭킹은 본질상 전반 스캔).
- ~~**평가가 검색/채택의 관문인가**~~ → **해결: "채택만 관문".** 평가 안 된 AI 초안도
  검색엔 그대로 보이되(찾아서 평가하게) **'초안'** 배지, 평가(스테이크)받으면 **'채택'**.
  숨기지 않고 라벨로 구분 — `_node_view.adopted = staked>0`, UI 초안/채택 배지.
- **사용성 시뮬레이션(멀티유저)에서 발견·완화한 2가지** (설계 귀결, 버그 아님):
  - *답 난립*: "묻기=항상 생성" 탓에 같은 질문이 초안을 양산. → 같은 질문(슬러그)의
    **채택본**이 있으면 `ask`가 새 초안 대신 그 답을 `stage:"existing"`으로 먼저 보여줌;
    `force:true`면 그래도 생성. (가시성·재사용 동선 강화, 생성권은 유지)
  - *평가자 콜드스타트*: harmonic 모델상 첫/단독 평가자는 후속 평가자가 와야 hub가 붙어
    hub=0·리더보드 부재. 핵심 공식은 불변(특허·테스트), 대신 점수판에 **'채택 평가자
    (스테이크)'** 랭킹을 추가해 평가 행위를 즉시 가시화.
- **옛 블롭 정리** — 정규화 검증 후 `nightwish_state` 드롭(전체 삭제 기능에 포함).

## 2026-06 — 허브 모드 시뮬레이션 → **harmonic 정본 유지** (노트 13)

세 모드(harmonic / count / sum=청구항3)를 4 시나리오로 비교(`/tmp/sim_hub*.py`).

| 시나리오 | harmonic | count | sum |
|---|---|---|---|
| **선견(S1)** A·B·C 허브 | 4 / 1 / 0.33 | 4 / 2 / 1 | **0 / 0 / 0 (죽음)** |
| **밴드왜건(S2)** A vs 늦은 L5 | 5 vs 0 ✓ | 5 vs 0 ✓ | 0 vs 0 |
| **폭주 10R** H : 일반 배율 | **30×** | 15× | (보정 시)15× |
| **시빌 vs 독립(S4)** | 6=6 ✗ | 6=6 ✗ | 6=6 ✗ |

**결정 및 근거:**
1. **`sum`(청구항 3 정본)은 *콜드스타트에 죽는다*.** 상속이 "밟는 이의 *현재* 허브"를
   곱하는데 초기엔 모두 0 → 아무도 허브를 못 얻음(S1·S2·S3 전부 0). 부트스트랩
   `base=1`을 더하면 살아나나(허브 6/2/1) *그건 더 이상 순수 청구항 3이 아닌 변형*이고
   count와 비슷해진다. → **정본 그대로 쓰기엔 부적합.**
2. **`count`(청구항 2)는 작동하나** 폭주가 harmonic의 *절반*이고 선견 차등이 완만(4/2/1)
   → 늦게 와도 꽤 받아 밴드왜건 억제가 harmonic보다 약함.
3. **`harmonic`(1/j)이 가장 균형** — 선견 차등 가장 가파름(4/1/0.33), 밴드왜건 억제
   최강(S2 L5=0), 콜드스타트 문제 없음. 유일 약점은 폭주 배율 최대(30×)이나, 이는
   *선견을 가장 강하게 보상*한다는 이면일 뿐 권위엔 영향 미미(S1 권위 셋이 유사).
4. **결정: 운영 정본 = `harmonic` 유지.** 청구항 2·3은 코드에 보존(계보·`NIGHTWISH_HUB_MODE`
   전환 가능), 운영 기본은 안 바꾼다.

**모든 모드 공통의 진짜 빈칸(S4): 시빌≡독립.** 세 모드 다 *패거리 5*와 *독립 5*를 구분
못 함(G=R=6). → 모드 선택으론 못 풀고 **로드맵 ③ '두루 집계'**(권위에 시빌 탐침의
독립-출처 가중)로만 메워진다. = 다음 작업.
